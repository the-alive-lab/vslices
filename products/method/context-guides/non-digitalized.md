# Non-digitalized work — Context Guide

**Owner:** VSlices Method. **Status:** migrated context guidance.

## Situation and principal risk

Important work occurs through conversation, paper, spreadsheets, messages, human memory, manual coordination or informal practice rather than adequate software representation. Lack of software does **not** imply simplicity.

**Risk:** automating poorly understood work, including temporary workarounds, implicit rules or historically contingent habits, as if they were permanent requirements.

## Method guidance

Start from **how work actually occurs**, not from predetermined screens, data models or features. Attend to actors, triggers, outcomes, variations, business vocabulary, manual decisions, exceptions and knowledge distributed between people.

The next action should preserve **only the relevant context** for deciding what matters and whether any software response is justified. Do not model the entire organization.

- **Context-First** can be useful where the reality of the work is broadly unclear.
- **Problem-First** can be useful when a particular manual-work problem is visible but poorly understood.
- **Slice-First** may be appropriate only when a small, meaningful and sufficiently safe realization can generate better evidence; being non-digitalized is not by itself a reason.

These are possible applications of [Modality Selection](../modality-selection.md), not a prescribed path. Existing public guidance suggests affinities for Business Scenario and Domain Context before Software Project, Customer Product or Consumable Service, but **the actual continuity at risk** determines which concepts/paths matter. Those documentary path definitions remain owned by Docs Standard.

Observed practice is **evidence**, not a prescription to reproduce it in code. Uncertainty and feedback must remain visible where they alter decisions.
